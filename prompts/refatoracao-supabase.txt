# PROMPT MESTRE: Migração Completa de API Node/MySQL para Supabase + Deploy Fullstack na Vercel

Você é um Arquiteto de Software especialista em Node.js, Express, PostgreSQL/Supabase e arquitetura Serverless na Vercel.
Sua missão é migrar este projeto que anteriormente rodava com MySQL local para o Supabase (PostgreSQL), preservando integralmente a estrutura da API Express existente (controllers, rotas e regras de negócio) e deixando o repositório 100% pronto para deploy na Vercel (raiz do projeto servindo o front-end estático e a API Serverless).

## 2. Regras de Ouro e Prevenção de Erros Críticos

Ao executar a migração, você **DEVE OBRIGATORIAMENTE** seguir estas diretrizes para evitar os erros comuns:

### Regra 1: Usar `@supabase/supabase-js` via HTTPS (Nunca conexão TCP direta `pg`/`mysql2`)
- **Problema:** Instâncias gratuitas do Supabase não fornecem IPv4 público direto (usam apenas IPv6 AAAA no host `db.<ref>.supabase.co`), resultando em `getaddrinfo ENOTFOUND` ou timeout em conexões locais e na Vercel. Além disso, drivers tradicionais que abrem conexão TCP esgotam pools em Serverless.
- **Solução:** Instalar e usar exclusivamente o cliente oficial `@supabase/supabase-js`. Ele opera sobre HTTPS (porta 443), é imune a bloqueios de rede, não vaza conexões e é nativamente otimizado para Serverless.

### Regra 2: Fallback Inteligente de Chaves de API (`Unregistered API key`)
- **Problema:** Chaves secretas fornecidas podem ter sido revogadas, digitadas com erro ou pertencer a outro projeto, gerando `401: Unregistered API key`.
- **Solução:** No arquivo de configuração do Supabase (`api/src/db/config.js`), priorize uma resolução em cadeia para a chave:
  ```javascript
  const supabaseKey = process.env.SUPABASE_KEY 
      || process.env.SUPABASE_PUBLISHABLE_KEY 
      || process.env.SUPABASE_SECRET_KEY;
  ```

### Regra 3: Row Level Security (RLS) e Políticas Permissivas (`Error 42501`)
- **Problema:** No Supabase, o RLS vem ativo por padrão. Se a chave usada na API for do tipo `publishable` / `anon`, qualquer `INSERT`, `UPDATE` ou `DELETE` no painel administrativo falhará com erro `42501: new row violates row-level security policy`.
- **Solução:** O script SQL de migração DEVE conceder privilégios (`GRANT ALL`) e criar políticas permissivas explícitas (`FOR ALL TO public USING (true) WITH CHECK (true)`).

### Regra 4: Carga Inicial de Dados (Seed Data Obrigatório)
- **Problema:** Apenas criar as tabelas deixa o banco vazio. O front-end abrirá sem categorias nem produtos, e o login administrativo falhará porque o usuário não existe.
- **Solução:** O script SQL deve incluir comandos `INSERT ... ON CONFLICT DO UPDATE` com:
  - 1 Usuário admin padrão (ex: `admin@mostruario.com` / `123456`)
  - 1 Loja oficial padrão (ID `1`)
  - Categorias padrão da loja
  - Produtos de exemplo com preços, estoque e fotos reais (Unsplash)
  - Sincronização de sequências (`setval(...)`) para que novos cadastros não gerem colisão de ID.

### Regra 5: Extensões `.js` Obrigatórias em Node ESM (`"type": "module"`)
- **Problema:** O `package.json` da API usa `"type": "module"`. O Node em modo ESM lança `ERR_MODULE_NOT_FOUND` se qualquer import relativo não contiver a extensão `.js` (ex: `import app from "./src/server"` falha; o correto é `import app from "./src/server.js"`).

### Regra 6: Servidor Híbrido (Local + Vercel Serverless)
- **Problema:** Se `app.listen()` estiver comentado, `npm start` local não roda. Se rodar incondicionalmente, a Vercel pode travar a função serverless esperando a porta fechar.
- **Solução:** No `api/src/server.js`, envolva o listen na condição:
  ```javascript
  if (!process.env.VERCEL) {
      app.listen(PORT, () => {
          console.log(`🚀 A API está rodando em http://localhost:${PORT}/api`);
      });
  }
  export default app;
  ```

### Regra 7: Estrutura Monorepo e Arquivos Estáticos na Vercel (`public/` vs `outputDirectory`)
- **Problema 1:** Se você configurar `"outputDirectory": "site"` em um projeto com preset Node.js, a Vercel tenta executar um servidor Node a partir da pasta `site/` e falha com o erro:
  `No entrypoint found in output directory: "site". Searched for: - app.js, index.js, server.js...`
- **Problema 2:** Se houver um script de build sem pasta de saída, a Vercel reclama de `STATIC_BUILD_NO_OUT_DIR` procurando por `public`.
- **Solução Definitiva:**
  1. Criar um script multiplataforma em `scripts/build.js` que sincroniza o conteúdo de `site/` para a pasta padrão `public/` esperada pela Vercel:
  ```javascript
  import fs from 'fs';
  import path from 'path';

  const srcDir = path.resolve('site');
  const destDir = path.resolve('public');

  if (fs.existsSync(destDir)) fs.rmSync(destDir, { recursive: true, force: true });
  fs.cpSync(srcDir, destDir, { recursive: true });
  ```
  2. No `package.json` da raiz:
  ```json
  {
    "type": "module",
    "workspaces": ["api"],
    "scripts": {
      "build": "node scripts/build.js",
      "start": "npm --prefix api start"
    }
  }
  ```
  3. No `vercel.json` da raiz (sem outputDirectory, usando a pasta `public` nativa):
  ```json
  {
    "version": 2,
    "rewrites": [
      { "source": "/api/(.*)", "destination": "/api" },
      { "source": "/admin", "destination": "/admin/login.html" }
    ]
  }
  ```

## 3. Plano de Execução Detalhado

### Passo 1: Dependências do Backend
Dentro da pasta `api`, instalar o client do Supabase e remover dependências antigas do MySQL:
```powershell
cd api
npm install @supabase/supabase-js
```

### Passo 2: Script SQL do Supabase (`banco-de-dados/supabase_migration.sql`)
Gerar o script PostgreSQL contendo:
1. `CREATE TABLE IF NOT EXISTS` para `usuarios`, `categorias`, `lojas`, `produtos` com tipos nativos do Postgres (`BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, `NUMERIC(10,2)`, `TEXT`, etc.).
2. RLS e Políticas:
   ```sql
   ALTER TABLE public.usuarios ENABLE ROW LEVEL SECURITY;
   ALTER TABLE public.categorias ENABLE ROW LEVEL SECURITY;
   ALTER TABLE public.lojas ENABLE ROW LEVEL SECURITY;
   ALTER TABLE public.produtos ENABLE ROW LEVEL SECURITY;

   CREATE POLICY "Acesso total usuarios" ON public.usuarios FOR ALL TO public USING (true) WITH CHECK (true);
   CREATE POLICY "Acesso total categorias" ON public.categorias FOR ALL TO public USING (true) WITH CHECK (true);
   CREATE POLICY "Acesso total lojas" ON public.lojas FOR ALL TO public USING (true) WITH CHECK (true);
   CREATE POLICY "Acesso total produtos" ON public.produtos FOR ALL TO public USING (true) WITH CHECK (true);

   GRANT ALL ON ALL TABLES IN SCHEMA public TO postgres, anon, authenticated, service_role;
   GRANT ALL ON ALL SEQUENCES IN SCHEMA public TO postgres, anon, authenticated, service_role;
   ```
3. Carga inicial com `ON CONFLICT DO UPDATE` e sincronização de sequências via `setval(pg_get_serial_sequence(...))`.

### Passo 3: Configuração da Conexão (`api/src/db/config.js`)
Substituir o pool MySQL pelo client do Supabase:
```javascript
import { createClient } from '@supabase/supabase-js';
import dotenv from 'dotenv';

dotenv.config();

const supabaseUrl = process.env.SUPABASE_URL;
const supabaseKey = process.env.SUPABASE_KEY 
    || process.env.SUPABASE_PUBLISHABLE_KEY 
    || process.env.SUPABASE_SECRET_KEY;

export const supabase = createClient(supabaseUrl, supabaseKey, {
    auth: { persistSession: false, autoRefreshToken: false }
});

export default supabase;
```

### Passo 4: Refatoração dos Controllers
Adaptar cada controller para consumir o Supabase mantendo rigorosamente os **mesmos contratos de resposta JSON** esperados pelo front-end:
- **`usuariosController.js`**: `supabase.from('usuarios').select('*').ilike('email', email)` para validar login.
- **`categoriasController.js`**: Listar (`select('*').order('id')`), Criar (`insert`), Atualizar (`update`), Deletar (`delete`).
- **`lojasController.js`**: Listar todas, buscar por ID e buscar por usuário.
- **`produtosController.js`**:
  - Listar com filtros dinâmicos: aplicar `.ilike()` para buscas textuais e categoria, e `.gte()` / `.lte()` para limites numéricos de preço e estoque.
  - CRUD completo validando integridade referencial antes do `insert` / `update`.
  - Mapear a resposta para devolver `{ produtos: [...] }` contendo `id`, `nome`, `descricao`, `preco`, `quantidade`, `imagem_url`, `id_categoria` e `nome_categoria`.

### Passo 5: Arquitetura de Deploy Fullstack na Vercel
1. **`package.json` na raiz**:
   ```json
   {
     "name": "projeto-web",
     "version": "1.0.0",
     "private": true,
     "workspaces": [ "api" ],
     "scripts": {
       "install:api": "npm install --prefix api",
       "build": "npm run install:api",
       "start": "npm --prefix api start"
     }
   }
   ```
2. **`vercel.json` na raiz**:
   ```json
   {
     "version": 2,
     "outputDirectory": "site",
     "rewrites": [
       { "source": "/api/(.*)", "destination": "/api/index.js" },
       { "source": "/api", "destination": "/api/index.js" },
       { "source": "/admin", "destination": "/admin/login.html" }
     ]
   }
   ```
3. **`.gitignore` na raiz**:
   Ignorar `node_modules`, `.env`, `api/node_modules` e `api/.env`.
